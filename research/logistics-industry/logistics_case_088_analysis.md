# 物流改善事例088 調査メモ

## 1. 事例の概要

対象資料：国土交通省「物流事業者における生産性向上ガイドライン 改善事例
088」

対象となる物流の流れを一般化すると、以下の4者で構成される。

1.  **商品を作る側**
2.  **出荷元の倉庫を運営し、商品を集めてトラックへ積む側**
3.  **実際にトラックで輸送する側**
4.  **商品を受け取り、在庫として保管する側**

改善前は、受け取り側の物流センターでトラックの長時間待機が発生していた。

資料では、ピーク時の平均待機時間として **240分（4時間）**
が示されている。

また、到着順に荷卸しする運用だったため、早く荷卸しを終えて次の仕事へ向かいたいドライバーが前日の夜から順番取りを行い、物流センター開門時に多数の車両が集中していた。

------------------------------------------------------------------------

## 2. 改善前に発生していた作業

資料から確認できる主な作業は以下。

-   トラック到着
-   荷卸し
-   荷卸し後の仕分け
-   積替え
-   格納場所を示すシール貼り
-   シールに従った再仕分け
-   帳票と照合した数量検品

特に、荷卸し後にも仕分け・検品等の作業が発生しており、物流センター側の処理に長い時間を要していた。

### 現時点で資料から断定できないこと

以下については、この資料だけでは工程間の関係を特定できない。

-   荷卸し・仕分け・格納・検品が完全な直列工程だったか
-   仕分け中にバースを占有し続けていたか
-   検品中にトラックがバースを占有していたか
-   各工程で同じ作業者・フォークリフト等を共有していたか
-   各工程が後続トラックの荷卸し開始をどの程度ブロックしていたか

したがって、これらをシミュレーションへ反映する場合は、実態を追加調査するか、モデル上で設定可能な条件として扱う必要がある。

------------------------------------------------------------------------

## 3. 実施された3つの施策

### 施策1：受け取り後に行っていた仕分けを、出荷前に実施する

改善前は、商品が受け取り側へ到着してから、倉庫内のどこへ格納する商品なのかに応じた仕分けを行っていた。

改善後は次のように変更した。

1.  **受け取り側**が、商品を最終的にどの場所へ格納するのかという情報を事前に提供する。
2.  **商品を作る側**が、その情報を出荷元倉庫へ提供する。
3.  **出荷元倉庫**が、その情報を使って格納場所別に事前仕分けする。
4.  仕分け済みの状態でトラックへ積み込む。
5.  受け取り側で行っていた仕分け作業を削減する。

つまり、

**「受け取ってから仕分ける」→「送る前に仕分けておく」**

という、作業を前工程へ移す施策である。

重要なのは、単純な作業高速化ではなく、**受け取り側が持っていた格納場所情報を上流へ事前共有したことで、上流側で処理可能になった**点。

------------------------------------------------------------------------

### 施策2：事前仕分け済み車両の優先荷卸場所を設定する

施策1を実施した車両について、受け取り側が専用の「優先荷卸場所」を設定した。

つまり、

-   通常の車両
-   格納場所別に事前仕分け済みの車両

を同じ条件で処理するのではなく、後者を優先的に処理できるようにした。

これは単純な「処理速度向上」ではなく、**車両の状態に応じて処理順序・利用する荷卸場所を変更する施策**と捉えられる。

### 現時点で断定できないこと

優先荷卸場所を設置したことで、

-   ドライバーが前日から並ぶ必要がなくなった
-   到着時間が分散した
-   朝の車両集中そのものが解消された

といった因果関係までは、この資料には明示されていない。

------------------------------------------------------------------------

### 施策3：RFIDによって数量検品を省略する

改善前は、受け取り側が帳票と商品を照合して数量検品していた。

改善後は以下の流れに変更した。

1.  輸送前日に、出荷元倉庫が商品に付けた電子タグ（RFID）へ製品明細情報を登録する。
2.  同じ情報を受け取り側へ事前送信する。
3.  トラック到着時、受け取り側で電子タグを読み取る。
4.  電子的に情報を照合する。
5.  従来の人手による数量検品を不要にする。

これは、

**「検品作業を速くする」のではなく、「検品という人手作業そのものを削除する」**

施策と捉えられる。

------------------------------------------------------------------------

## 4. 定量効果

資料では、輸送時間を除くドライバーの労働時間について、

**400分 → 130分**

まで削減したとされている。

削減率は **約68%**。

また、以下の効果も示されている。

-   ドライバーの労働時間短縮
-   トラック回転率向上
-   削減した時間を利用した再運行が可能
-   受け取り側物流センターのスペース効率向上
-   荷卸場所の回転率向上

# 6. 特に重要な「工程間依存」の変数

今回の会話で重要な論点になった部分。

単純に、

`荷卸し時間 = 40分`

のような処理時間だけを持っていても、待ち時間への影響を正しく計算できない可能性がある。

例えば、現場が次のような完全直列運用なら、

``` text
トラック到着
  ↓
荷卸し
  ↓
検品
  ↓
仕分け
  ↓
格納
  ↓
バース解放
  ↓
次のトラック
```

仕分けを30分短縮すれば、バース解放も30分早まり、後続車両の待ち時間へ直接影響する。

一方、

``` text
                 ┌→ 検品
トラック → 荷卸し ├→ 仕分け
                 └→ 格納

荷卸し終了時点でバース解放
```

という並列的な運用なら、仕分け時間を短縮しても、トラックの待ち行列にはほとんど影響しない可能性がある。

したがって、シミュレーターでは単純な作業時間だけでなく、

-   **工程Aが終わらないと工程Bを開始できないか**
-   **どの工程終了時点でトラックを解放できるか**
-   **どの工程終了時点でバースを解放できるか**
-   **工程同士が同じ人員を取り合うか**
-   **工程同士が同じ設備を取り合うか**
-   **工程を並列実行できるか**

という、**工程間の依存関係とリソース競合**を表現できる必要がある。

これはMVP変数を決める際の重要な検討事項。

------------------------------------------------------------------------

# 7. 今回事例から抽出できる「施策の最小単位」

結果ではなく、シミュレーション上で操作できる変更として分解する。

### 情報を動かす

-   格納場所情報を受け取り側から上流へ事前共有する
-   商品情報を輸送前に受け取り側へ送信する

### 作業する場所・タイミングを動かす

-   到着後の仕分けを出荷前へ移す
-   格納場所別に事前仕分けする

### 処理順序を変える

-   条件を満たした車両を優先処理する
-   車両ごとに利用する荷卸場所を変える

### リソースを増減・専用化する

-   特定車両用の優先荷卸場所を設定する

### 作業そのものを削除する

-   RFIDを導入する
-   製品情報を電子タグへ事前登録する
-   電子的に照合する
-   人手による数量検品を廃止する

------------------------------------------------------------------------

# 8. 今回事例から得られた設計上の重要な示唆

今回の事例では、単純に、

> トラックの到着時刻を最適化する

だけでは表現できない改善が多い。

待ち時間は、

**到着 → 荷卸し → 検品 → 仕分け → 格納**

という物流センター内部の処理能力からも発生する。

さらに、改善施策は単純な「作業高速化」だけではない。

-   情報を前もって渡す
-   作業を前工程へ移す
-   処理順序を変える
-   専用リソースを設ける
-   作業そのものをなくす

といった異なる種類の変更が存在する。

したがって、MVPを検討するときには、

**「配送計画の変数」だけでなく、「拠点内部の処理工程・リソース・工程間依存をどこまでモデル化するか」**

を決める必要がある。

今回の事例だけでは、実際の工程間依存関係までは確認できない。そのため、ここを無根拠に固定して実装するのではなく、追加事例を調査しながらMVPで必要な抽象度を決定する。
